# fastest-finger

VOICEPEAK で作成した音声を用いた早押しクイズ。

音声の再生に合わせて問題文が少しずつ表示され、早押しで停止・回答できる。

## 構成

このリポジトリは 2 つのアプリを含む。

| ディレクトリ | 内容 |
| --- | --- |
| `poc/` | フロントエンド単体の PoC。1 台のブラウザで完結する（[詳細](#poc)） |
| `server/` | バックエンド（Python / FastAPI）。オンライン版の早押し判定（[詳細](#オンライン版)）と、LLM API の中継（[詳細](#llm-による問題予測)）を担う |
| `web/` | オンライン版のフロントエンド。出題者用（投影）と回答者用（スマホ） |

出題データとジングル SE はリポジトリルートに置き、両者で共有している。

```
fastest-finger/
├── quiz_data/     問題データ（CSV と VOICEPEAK の出力）
├── sound/         ジングル SE
├── poc/           PoC（フロントエンド単体）
├── server/        バックエンド（オンライン版の判定・LLM 中継）
└── web/           オンライン版フロントエンド
```

`poc/public/quiz_data` と `poc/public/sound` は、ルートの共有ディレクトリへの
シンボリックリンク。PoC からは従来どおり `/quiz_data` `/sound` の URL で配信される。

## 必要なもの

- Node.js 20 以上
- オンライン版、または PoC の LLM 予測を動かす場合は、
  追加で Python 3.12 以上と [uv](https://docs.astral.sh/uv/)
- LLM 予測を使う場合は、各社の API キー

## セットアップ

```bash
npm install
```

npm workspaces 構成のため、リポジトリルートで実行する。

## 出題データの配置

**出題データとジングル SE はリポジトリに含まれていない**（`.gitignore` で除外）。
各自でローカルに配置する。

ただしデータ形式のサンプルとして、`questions_example.csv` と
対応する 1 問分の音声（`20260820/0-20260820.wav` / `.txt` / `.lab`）のみ追跡している。
`questions_example.csv` を `questions.csv` にコピーすれば、この 1 問で動作する。

```bash
cp quiz_data/questions_example.csv quiz_data/questions.csv
```

### 1. 問題データ — `quiz_data/`

問題文と正解は `questions.csv` で管理し、VOICEPEAK の出力ファイルは
**リネームせず**バッチ（日付）フォルダにそのまま置く。

```
quiz_data/
├── questions_example.csv   ← サンプル（追跡対象）
├── questions.csv           ← 実データ（各自で用意）
└── 20260821/          ← バッチ = VOICEPEAK プロジェクト 1 つ
    ├── 00-20260821.wav / .txt / .lab
    ├── 01-20260821.wav / .txt / .lab
    ├── ...
    ├── 10-20260821.wav / .txt / .lab
    ├── 20260821.txt   ← 使用しない（VOICEPEAK の全体出力）
    ├── 20260821.lab   ← 使用しない（VOICEPEAK の全体出力）
    └── 20260821.vpp   ← 使用しない（VOICEPEAK プロジェクト）
```

`questions.csv` は 5 列。

```csv
batch,seq,text,answer,alt_answers
20260821,0,日本で一番高い山は富士山ですが、世界で一番高い山はどこ？,エベレスト,
20260821,1,大蛇を意味する名を持つプログラミング言語は何でしょう？,Python,パイソン|ニシキヘビ
```

| 列 | 内容 |
| --- | --- |
| `batch` | バッチ名（`YYYYMMDD`）。`quiz_data/{batch}/` に対応 |
| `seq` | VOICEPEAK が出力した連番（0 起点）。`{seq}-{batch}.wav` などに対応。**整数で書く**（`0` でも `00` でも同じ） |
| `text` | 問題文。**改行を含めない**（1 問 1 ブロック） |
| `answer` | 正解 |
| `alt_answers` | 別解。`\|` 区切りで複数指定可。無ければ空 |

VOICEPEAK は連番を 0 起点でしか振れず接頭語も付けられないため、
バッチフォルダと連番の組で一意性を与えている。

ファイル名が `{seq}-{batch}` となっているのは、VOICEPEAK が連番だけの出力を
許さず接尾語が必須のため。接尾語にはバッチ名（日付）をそのまま指定する。
フォルダ名と接尾語が一致するので、別の日のファイルを取り違えて置いた場合に
参照先が見つからず検出できる。

##### 連番のゼロ埋め

VOICEPEAK は、**同じ接尾語で出力したファイル数**に応じて連番をゼロ埋めする。

| 1 バッチの出力数 | 連番 |
| --- | --- |
| 9 個以下 | `0`〜`8`（ゼロ埋めなし） |
| 10〜99 個 | `00`〜`99`（2 桁） |
| 100 個以上 | `000`〜（3 桁） |

境界は連番の値ではなく**出力数**で決まる。9 個なら 1 桁、10 個なら 2 桁になる。

桁数はバッチ内の `seq` の最大値から自動で判定するため、`questions.csv` には
**整数で書けばよい**（`0` でも `00` でも同じ結果になる）。表計算ソフトで開くと
ゼロ埋めは数値として桁落ちするので、CSV 側の表記に依存しない作りにしている。

##### 同居してよいファイル

VOICEPEAK は連番ファイルとは別に、全体を連結した `{batch}.txt` / `{batch}.lab` も
出力する。また出力元のプロジェクトファイル `{batch}.vpp` を同じフォルダで管理すると
分かりやすい。いずれも本システムからは使用しないが、**置いたままで問題ない**
（`questions.csv` 起点で参照するため、これらを読みに行くことはない）。

#### 問題を追加する手順

1. `questions.csv` の `text` 列を表計算ソフトでまとめて選択し、VOICEPEAK に貼り付ける
   （改行がそのままブロック分割になる）
2. `quiz_data/{バッチ名}/` へ連番出力する。**接尾語にはバッチ名（日付）を指定する**
   （10 問なら `00-20260821.wav`〜`09-20260821.wav` のようになる）
3. `npm run manifest -w poc` を実行する

CSV の `text` と出力された `.txt` の中身が一致しない場合、
どの行がズレているかを報告してビルドが止まる。
同日に作り直す場合は、同じフォルダへ先頭から再出力する。

### 2. ジングル SE — `sound/`

| ファイル名 | 再生タイミング |
| --- | --- |
| `set.WAV` | 出題時（この再生完了後に問題音声が始まる） |
| `buzz.WAV` | 早押し時 |
| `correct.WAV` | 正解時 |
| `wrong.WAV` | 不正解時 |

## PoC

フロントエンド単体構成。1 台のブラウザで出題から回答までを行う。

### 起動

```bash
npm run dev -w poc
```

`dev` / `build` は、実行前に `questions.csv` を読んで
問題一覧 `manifest.json` を自動生成する。データを追加・削除した際は再実行する。

manifest だけを作り直したい場合:

```bash
npm run manifest -w poc
```

### 操作

1. 「開始」を押すとジングルが鳴り、続いて問題音声が再生される
2. 再生に合わせて問題文が表示されていく
3. **スペースキー** または画面中央のボタンで早押し（音声と表示が止まる）
4. 答えを入力して「回答」を押すと正誤判定
5. 「次へ」で次の問題へ

早押しせずに最後まで再生された場合も、そのまま回答できる。

### 仕組み — 音声と問題文の同期

音素ラベル（`.lab`）と日本語表記（`.txt`）は文字数が対応しないため
（例: 「日本」= `n i cl p o N`）、以下の方式で対応付けている。

1. `.lab` の無音区間（`pau`）で音声を発話チャンクに分割する
2. `.txt` を読点・句点で同数のチャンクに分割し、順に対応付ける
3. チャンク内部は、時間の経過割合に応じて文字を送る

VOICEPEAK の読み上げでは `pau` が読点の位置とよく一致するため、
チャンクの境目で表示が実際の読み位置に追従する。

同期ロジックは [`poc/src/lib/align.ts`](poc/src/lib/align.ts) に閉じ込めてあり、
より高精度な方式（読み仮名を付与して音素列とアライメント）へ差し替えられる。

### ファイル構成

```
poc/
├── scripts/build-manifest.ts   questions.csv の検証と manifest.json の生成
└── src/
    ├── App.tsx                 画面全体と音声再生の制御
    ├── state/quizMachine.ts    出題サイクルの状態遷移
    ├── lib/
    │   ├── lab.ts              .lab パーサ（HTK 形式 → 秒、pau 区間の抽出）
    │   ├── align.ts            音声と問題文の対応付け
    │   ├── answer.ts           正誤判定（正解・別解との照合）
    │   ├── manifest.ts         問題の読み込みと抽選
    │   └── sound.ts            ジングル SE の再生
    └── components/             画面パーツ
```

## LLM による問題予測

途中まで読み上げられた問題文から、LLM に続きを予測させて答えを出させる機能。
人間の早押しと並べて、どこまで当てられるかを観測する。

現在は **OpenAI のみ対応**（Claude / Gemini / xAI Grok は今後追加）。

### 仕組み

API キーはブラウザのバンドルに埋め込めず、各社 API にはブラウザからの直接
呼び出しに CORS 制限があるため、`server/` が中継する。

```
poc (vite :5173) ──/api/llm/* をプロキシ──▶ server (:8000) ──▶ 各社 API
```

**問題文の全文と正解はサーバへ送らない。** LLM へ渡すのは早押し時点で画面に
出ていた文字列だけで、正解は PoC 側が保持したままにする。

### セットアップ

```bash
cp server/.env.example server/.env
```

`server/.env` に使うプロバイダのキーを設定する。キーが未設定のプロバイダは
利用不可として扱われ、PoC の選択肢に現れない。

| 環境変数 | 用途 |
| --- | --- |
| `OPENAI_API_KEY` | OpenAI |
| `LLM_PLAIN_ANSWER_MAX_LENGTH` | 読み切り時に平文の答えを許容する最大文字数（既定 30） |

### 起動

```bash
cd server && uv run uvicorn app.main:app --port 8000
```

疎通確認:

```bash
curl http://localhost:8000/api/llm/health
```

### 出題データが無くても起動する

この機能は出題データに依存しないため、`questions.csv` の検証に失敗しても
サーバは起動し、`/api/llm/*` は使える。

ただし **オンライン版の入口（`/host` `/player` `/ws`）は 503 で閉じる**。
問題 0 件のまま出題できてしまうと、原因が分からないまま遊べない状態になるため。
起動時のログに、読み込めなかった理由が出る。

### 応答フォーマット

JSON で返すようプロンプトで指示する。OpenAI の `response_format` などによる
JSON 強制は**使わない**。指示に従うかどうかの観測もこの機能の目的であり、
強制すると違反が発生しなくなるため。

早押しで止めた場合（続きの予測あり）:

```json
{ "continuation": "<補完した問題文の全文>", "answer": "<答え>" }
```

読み切った場合（続きの予測なし）:

```json
{ "answer": "<答え>" }
```

読み切り時に限り、短い平文の応答もそのまま答えとして扱う（既定 30 文字まで）。
これを超える平文や、JSON として解釈できない応答は**応答フォーマット違反**とする。
違反はエラーではなく、モデルが指示に従わなかったという観測結果として扱う。

### プロンプト

`partial_text` が早押しクイズの問題文であることを必ず伝える。これを省くと
「日本で一番高い山は富士山です」から「富士山は静岡県と山梨県の県境にあり…」
のような説明文が補完され、問いの形にならず答えを出せない。

「〜ですが、」で前半を振ってから後半で別を問う形式（パラレル問題）が頻出する
ため、前半の語がそのまま答えとは限らないことも指示に含めている。

プロンプトはプロバイダ間で共通のものを使い、社ごとの最適化はしない。
社ごとに変えると予測精度の比較が公平でなくなるため。

### ファイル構成

```
server/app/llm/
├── config.py            .env の読み込みと閾値
├── prompt.py            プロンプト生成（早押し用 / 読み切り用）
├── parser.py            応答の解釈と違反判定
├── base.py              プロバイダの共通契約とエラー正規化
├── registry.py          プロバイダ一覧
├── openai_provider.py   OpenAI
└── router.py            /api/llm/health, /api/llm/predict
```

## オンライン版

出題者用（投影）と回答者用（スマホ）を分け、**誰が最初にボタンを押したか**の判定を
Python バックエンドが行う。正誤判定は出題者が口頭回答を聞いて ○/× ボタンで下す。

同一 WiFi ネットワーク内での利用を想定している（オープンネットワークは想定外）。

### 起動

```bash
npm install
npm run build -w web
cd server && uv sync && uv run uvicorn app.main:app --host 0.0.0.0 --port 8000
```

起動すると、出題者用 URL（トークン付き）と参加者用 URL が表示される。

```
  問題数: 2 問

  出題者用: http://localhost:8000/host?token=xxxxxxxxxxxx
  参加者用: http://192.168.x.x:8000/player
```

- **出題者用** URL を投影 PC で開く。参加用 QR コードが画面に出る
- **参加者**は QR を読み取り、名前を入力して参加する

`questions.csv` の検証に失敗した場合、サーバは起動するが**オンライン版は使えない**
（`/host` `/player` `/ws` が 503 を返す）。どの行が問題かを起動時に表示するので、
直してから再度起動する。

サーバ自体を起動させるのは、[LLM 中継](#llm-による問題予測)が出題データに
依存しないため。問題 0 件のまま出題できてしまうと、原因が分からないまま
遊べない状態になるので、オンライン版の入口だけを明示的に閉じている。

> [!IMPORTANT]
> `--workers` は増やさないこと。ルームの状態はプロセス内のメモリに持つため、
> ワーカーが 2 つ以上あると参加者ごとに別の状態を見ることになる。

### 開発時

バックエンドとフロントを別々に動かす。Vite の dev server が `/api` `/ws` `/quiz_data`
`/sound` をバックエンドへ中継するので、ブラウザからは同一オリジンに見える。

```bash
# 1 つ目のターミナル
cd server && uv run uvicorn app.main:app --port 8000 --reload

# 2 つ目のターミナル
npm run dev -w web
```

出題者用は `http://localhost:5173/host.html?token=...`、
回答者用は `http://localhost:5173/player.html` で開く。

### テスト

```bash
cd server && uv run pytest
```

早押しの「最初の一人」判定や、古いラウンドの排除は複数端末での同時押しを
手動で再現できないため、単体テストが唯一現実的な検証手段になる。

### 操作の流れ

1. 出題者が「出題する」を押す。ジングルが鳴り、続いて問題音声が流れる
2. 問題文は読み上げに合わせて投影画面に表示される（回答者の画面には出ない）
3. 誰かが早押しすると、**サーバが最初の一人を決める**。音声と文字送りが止まり、
   その人の名前が投影される。押した本人の画面には「回答権」が出る
4. 回答を聞いたら出題者が「チェック」を押す。**ここで初めて正解が投影に出る**
5. 「正解」「不正解」を押して判定する
6. 「次の問題へ」で次へ進む

読み切っても自動では締め切らない。「読み切りました（まだ押せます）」の状態が続き、
出題者が「タイムアップ」を押して初めて締め切られる。読み切ってから数秒は
押させるのが通例のため。誰も押さなければ、そこで正解を出してスルーする。

**正解を投影に出すのは「チェック」「タイムアップ」を押した後だけ。** 投影画面は
参加者も見るので、回答権を得た時点で正解が見えていると、それを読んで答えられて
しまう。表示するかどうかをフロントに委ねず、サーバが送る phase を絞ることで担保
している。

押し間違いは「解除して続ける」で取り消せる。判定を経ていないので、その人は
お手つきにならず、また押せる。不正解と判定した場合はその問題は終わりで、
同じ問題で 2 人目の早押しを受け付ける運用（ダブルチャンス）は行わない。

### 仕組み

| 項目 | 方式 |
| --- | --- |
| 早押し判定 | サーバがメッセージを受け取った順。端末の時計は使わない |
| 正解の秘匿 | 出してよい phase 以外はサーバが送らない（投影は参加者も見るため） |
| 排他 | asyncio の単一イベントループの直列性に任せる（ロックなし） |
| 古い押し込みの排除 | `round_id` が現在のラウンドと一致しない `buzz` は捨てる |
| 状態の同期 | 差分ではなく状態全体を配る。再接続は繋ぎ直すだけで復元される |
| 文字送り | 出題者フロントが `.lab` から計算する。サーバは介在しない |
| 参加者の同一性 | サーバ発行の token を `localStorage` に持つ。リロードしても復帰する |
